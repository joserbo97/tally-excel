Settings as in the panel: thinking = low, 32K context, temperature 0.6, web off. Each task ran 3 times.

## Core tier: 27 tasks × 3 = 81 runs

**Corrected result: 79 / 81 passed (97.5%).** The raw score was 95%. Three runs were re-scored or re-run because the benchmark itself had bugs, all now fixed and covered by `npm run bench:selftest`:

| What happened | Cause | Fix | Re-run result |
|---|---|---|---|

The sum landed in **E52/F52 instead of D52**, under no column, and its reply claimed the total was in C52:D52. The value was correct; the placement and the description were wrong. This is a consistent weakness in counting columns when writing a row that starts with a label.

Six of seven tasks passed 3 out of 3. The reconciliation passed 1 out of 3.

**Reconciliation is the weak spot, and the cause is overthinking.**
- **Rounds 1 and 2:** the model compared the two sheets **in its head**.
  - In round 1, one thinking step ran 7 min 55 s (about 16K tokens), and it timed out before writing anything.
  - In round 2 the same approach finished correctly with 3.5 min to spare.
- **Round 3:** it chose the right method, a helper sheet with `COUNTIF` formulas, but only after a 9 min 43 s thinking step. It ran out of time while building the sheet. Its last ~3 minutes overlapped the other GPU job; the long step ran alone, so the result stands.

Two possible fixes:
- a system-prompt rule: for comparisons over ~30 rows, use formulas or code, and plan briefly;
- for list-matching tasks, a lower thinking level.

**Most tool errors don't count against the model.**
- In scenario-switch, the agent tried to add a dropdown (data validation) to the selector, and the stand-in workbook has no data-validation support. Its first attempts (`dv.type = …`) would fail in real Excel too.
- The one genuine model slip was in round 3's 3,000-row task: it set `range.values = null`. It recovered on the next step.

### Fixes made during this run

- **The agent now handles empty steps.** In an aborted first attempt, the amortization task ended after a step with 6,282 tokens of thinking and *no reply and no tool call*, and the agent treated that as the final answer. Now it:
  - recovers a tool call the model wrote inside its thinking;
  - otherwise nudges the model to continue, at most twice.

  The panel hides that nudge in saved chats. The behaviour is covered by `scripts/test-agent-loop.mjs`, which is part of `bench:selftest`. In the 21 runs above, no empty step occurred.
- **A checker bug was fixed.** The month-grid checker crashed when the agent used real dates (`=DATE(2026,1,1)` shown as `yyyy-mm`) as month labels instead of text. There is now an extra reference solution with date labels, and the self-test passes 35 of 35.

### Fixing the reconciliation weakness (tried; changes 1 and 2 reverted)

Three changes to the agent, tried one after another:

1. **Prompt rule:** "let Excel do the comparing". For matching or reconciling more than ~20 rows, write COUNTIF / XLOOKUP / SUMIF / FILTER / UNIQUE formulas in a helper column or sheet, keep planning short, and never type the same formula into many rows.
   - Re-test: 1 pass (191 s, but still compared in its head), then 1 timeout. The timeout was one 11 min 9 s model call with nothing else on the GPU.
   - The rule alone doesn't stop the overthinking.
2. **Thinking cap**, enforced by the agent rather than by asking the model. When a step's thinking exceeds ~6K tokens (24K chars) at think=low, or ~12K at medium, the agent cuts the step off, adds a hidden "stop planning and act now" nudge, and runs the next step without thinking. After two cuts, thinking stays off for the rest of the turn. There is no cap at xhigh.
   - Re-test: 1 pass (122 s), then 1 timeout.
   - The timeout was a different cause. The model created a helper sheet, then spent 5–6 minutes per step generating a huge tool call, typing ~60 rows of formulas one by one. Ollama sends a tool call only when it's complete, so the thinking cap can't see this.
3. **`write_range` fill-down:** a new `fill_down_to_row` option. The model writes one formula row, and the tool copies it down with relative references shifted ($-anchored refs stay), like Excel's fill handle. The prompt rule now points to it, or to a single spilling FILTER/UNIQUE formula.
   - Re-test: incomplete. The battery reached 15% about 10 minutes into the first run, so the run was stopped.
   - Until then it was progressing in short steps, with two ~3.5-minute steps that match the cap firing.

Supporting changes, all covered by `npm run bench:selftest`:
- The stand-in workbook now shows **spilled** results (FILTER/UNIQUE) to the checkers and in the used range, as Excel does. Before, a correct FILTER solution would have been scored as wrong.
- New tests:
  - a formula-only reconciliation reference solution;
  - `scripts/test-fill-down.mjs` (12 checks);
  - agent-loop cases in `scripts/test-agent-loop.mjs`, including that Stop still aborts (the thinking-cap cases were dropped with the cap).
- The shift logic moved to `public/js/formulas.js`, shared by the real tool and the stand-in.

**Conclusion:**
- The prompt rules and the thinking cap did **not** fix reconciliation.
- They may have cost something elsewhere, but these are single runs, so the evidence is weak.
- The useful lasting gains are in the tooling and the benchmark:
  - `fill_down_to_row`, which the model used correctly in 4 runs;
  - spilled results visible to the checkers;
  - the reconciliation checker accepting helper columns, with two must-fail cases;
  - each run's changed cells saved in the results JSON.

**Decision (2026-11-16):** the two prompt rules and the thinking cap were **removed** from the agent and the panel; the system prompt and thinking behaviour are back to what they were for the 19/21 hard-tier run. Kept: `fill_down_to_row` (its tool description still points the model to it), the empty-step handling, and all the benchmark fixes. `scripts/test-agent-loop.mjs` now checks instead that long thinking is never cut off and that Stop still aborts.

**Known gap in the stand-in:** spill references (`A2#`) aren't supported yet. Until they are, results on tasks where the model reaches for them are pessimistic.

## What this says so far

- On everyday Excel work (the core tier), qwen3.8 through this agent is **reliable**: 97.5% across 81 runs, always using live formulas.
- On harder multi-step work (the hard tier), it passed 19 of 21 (90%), with every result built from live formulas. It is slower than a cloud model: 1–4 min for most hard tasks and up to 8.5 min for the amortization schedule and reconciliation.
- It has two repeatable weaknesses:
  1. **Sloppiness when writing a mixed row:** the total lands in the wrong column, and the agent then misreports where it is. A possible agent-side fix is to re-read the written range after writing and compare it with what was intended.
  2. **Overthinking list comparisons** (reconciliation): 8–10 minutes of thinking before acting, sometimes comparing in its head instead of with formulas. This caused both hard-tier failures.
- A comparison with Claude needs the same tasks run with a Claude backend. The harness supports that once a Claude model option exists in the agent.
